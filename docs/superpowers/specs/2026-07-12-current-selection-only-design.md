# Pot 当前选区独立翻译设计

## 背景

翻译窗口为降低 Ctrl+D 弹出延迟改为隐藏后复用 WebView，但用户配置仍开启了“增量翻译”。因此划词和 OCR 的新结果会继续拼接到常驻的旧源文中；置顶窗口下该问题更加稳定复现。历史记录已经证明本次选区被正确取得，只是被追加在旧文本末尾。

## 目标

- 每次 Ctrl+D 只翻译本次选中的文字。
- 每次 OCR 翻译只翻译本次识别结果。
- 保留翻译窗口复用，不能重新引入 WebView 冷启动延迟。
- 输入翻译、动态翻译、Markdown 与 LaTeX 渲染行为保持不变。

## 方案比较

### 方案 A：只修改本机配置

把 `incremental_translate` 改成 `false`。改动最小，但其他用户或未来误开启开关后仍会复现，源码回归仍然存在。

### 方案 B：仅在窗口隐藏后重置

保留置顶窗口内的连续追加，只阻断跨隐藏会话累积。它不能解决本次置顶窗口场景：用户选中下一段文字时窗口仍可见，旧文仍会被追加。

### 方案 C：划词与 OCR 始终替换源文（采用）

删除隐式增量追加入口，每个取词事件都以本次文本作为完整源文；同时移除会误导用户的“增量翻译”开关。该方案与用户明确的“我只选了这些词”一致，也彻底消除窗口生命周期对源文语义的影响。

## 数据流

1. Rust 继续复用翻译窗口并发送 `new_text`，不改变低延迟窗口时序。
2. `SourceArea` 对划词和两条 OCR 成功回调统一计算本次源文。
3. OCR 开始时立即清空并同步旧源文；识别成功、失败和语言检测出口都校验同一请求编号，较晚返回的旧 OCR 不得覆盖更新的划词或 OCR。
4. 同步更新 `sourceTextRef`、本地源文状态和 Jotai 原子，后续语言检测与翻译只收到本次文本。
5. 旧配置键允许留在现有 JSON 中，但前端不再读取；本机值同时改为 `false`，便于旧版本回退时也不会继续累积。

## 错误处理

当前 OCR 请求的错误文本继续替换当前源文并显示，不与旧结果拼接；已经过期的 OCR 成功或失败回调均被丢弃。空选区明确清空源文和译文，不能继续展示上一选区。

## 测试

- 纯函数回归：即使旧配置传入“开启增量”，下一源文也必须等于本次文本。
- 源码契约：划词、插件 OCR、内置 OCR 都不得使用 `old + newText`。
- 竞态回归：慢 OCR A 在新选区 B 之后返回时，不得覆盖 B；OCR 等待阶段不得显示旧源文。
- 配置界面契约：不再展示或读取 `incremental_translate`。
- 运行 `node --test src/utils/translation_flow.test.js`、`npm run build` 和 `cargo check`。

## 迁移策略

无迁移，直接替换。旧的增量配置键失效，不保留兼容行为。
