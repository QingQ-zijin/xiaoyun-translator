# Pot Ollama OCR 设计

## 背景

当前截图翻译由系统 OCR 或 Tesseract 先把截图转成纯文本，再交给翻译服务。它们不理解公式结构，容易破坏上下标、分式和 Markdown；通用 Gemma 视觉模型在本机测试中又会补写截图之外的内容。此前重复旧文本的问题已经在请求隔离层修复，本次只解决当前截图的识别质量与启动延迟。

## 目标

- Ctrl+E 每次只识别本次框选截图，不携带聊天历史或旧图片。
- 中英文、Markdown 与 LaTeX 混排时保留阅读顺序和结构。
- 热启动目标小于 2 秒，冷启动不阻塞窗口弹出。
- 模型异常、空输出或无法收敛时可回退系统 OCR。
- 快速连续截图时取消旧模型请求，避免旧任务占用 GPU 队列。

## 同图 A/B 结果

测试输入为 Pot 当前真实截图裁剪，包含标题 `Stoichiometric matrix, S` 与四行带下标公式。测试图片仅用于本机验证，不进入仓库。

| 引擎 | 模式 | 冷启动 | 热启动 | 结果 |
| --- | --- | ---: | ---: | --- |
| GLM-OCR 1.1B F16 | 轻量预处理、`OCR:`、流式重复守卫 | 约 6 秒 | 1.53 秒 | 标题、四行公式、变量大小写与 LaTeX 全部正确 |
| PaddleOCR-VL 1.6 BF16 direct | `OCR:` | 3.91 秒 | 0.66 秒 | 标题前缀乱码，多处小写 `v` 错成大写 `V` |
| PaddleOCR-VL 1.6 BF16 direct | `Formula Recognition:` | 已热载 | 3.92 秒 | 未停止并从 `V_1` 幻觉扩展到 `V_85` |

PaddleOCR-VL 的完整官方文档解析成绩依赖布局检测、区域分类、分块识别与阅读顺序合并；本次 Pot 输入已经是用户裁剪的小区域，直接 VLM 才是可比路径。基于真实输入结果，默认采用 GLM-OCR。Paddle 模型保留为本机实验资产，不作为 Pot 默认值。

## 方案比较

### 方案 A：继续系统 OCR，再用大模型修复

无法从已经丢失的上下标和分式可靠还原原图，且串联两次推理增加延迟，不采用。

### 方案 B：把截图交给现有翻译模型

改动少，但通用模型会解释、翻译或补写内容，无法保证逐字识别，不采用。

### 方案 C：新增专用 Ollama OCR 服务（采用）

新增内置识别服务 `ollama_ocr`，默认连接本机 `glm-ocr:latest`。它只发送当前 base64 图片与固定 `OCR:` 指令，不复用消息上下文。内部使用流式生成，以便在确认模型开始重复首段时立即中止，而不是等待上下文耗尽。

## 请求与数据流

1. Rust 截图流程继续把当前裁剪保存并通过 `get_base64` 返回。
2. `ollama_ocr.recognize` 先取消同服务尚未结束的旧请求，再创建本次请求。运行时直接持有 `AbortController`，因此 HTTP 建连、等待首响应和流式读取阶段都可取消。
3. 小于 900 像素的裁剪使用 2 倍高质量放大，并按四角平均背景色增加 32 像素边距；大图只增加 16 像素边距。该步骤解决贴边标题和小号上下标漏识别，同时限制视觉 token。
4. 请求体固定包含处理后的当前一张图片、`OCR:`、`stream: true`、温度 0、固定随机种子、重复惩罚、硬输出上限和 30 分钟模型保活；不包含历史消息或旧图片。
5. 流式缓冲区持续执行保守重复检测。确认重复后中止网络流并返回第一次完整正文。
6. 输出校验失败时，按配置调用系统 OCR；回退把本次原始 base64 写入请求独占的临时文件，不再读取可能被下一次截图覆盖的共享文件。
7. 管线在模型流和系统回退完成后都复检请求代次；调用层另有 request id 守卫，过期结果不得覆盖更新的截图或划词结果。

## 重复守卫

GLM-OCR 的实测异常不是旧缓存，而是正确首段之后重新打开 `markdown` 围栏并再次生成首段。守卫只在以下证据同时成立时截断：

- 围栏为顶层 `markdown`、`md` 或 `text` 围栏；
- 围栏前已有足够正文；
- 围栏后至少生成一段可比较前缀；
- 忽略 Unicode 规范化与空白后，该前缀与首段开头完全相同。

比较过程不会删除 Markdown 或 LaTeX 标点，返回值直接切取原始缓冲区，因此 `**粗体**`、`$x_i$`、`$$...$$` 和反斜杠保持不变。另设仅在输出达到长度上限时启用的多行精确循环兜底；不做公式语义或模糊去重，避免把本来相似的多行公式合并。

## 配置与界面

服务配置只暴露四项：实例名称、Ollama 地址、模型名称、失败时回退系统 OCR。默认地址为 `http://localhost:11434`，默认模型为 `glm-ocr:latest`。模型下载仍由用户显式执行，配置页只检查 Ollama 与模型是否可用，不在保存时隐式下载大文件。

`ollama_ocr` 的元数据声明结构化输出。模型成功时，截图识别窗口与截图翻译窗口即使开启“删除换行”也跳过压平处理，以免破坏 Markdown 与 LaTeX；若本次实际回退到系统 OCR，则通过结果元数据恢复普通文本的既有行为。

## 错误与取消

- 新截图到来：即使旧请求还在等待首个 HTTP 响应或系统 OCR 回退，也立即取消并作废；旧请求不再写回结果。
- Ollama 连接、模型加载或生成失败：启用回退时调用系统 OCR。
- 空输出、只有围栏、达到硬上限且无法可靠去重：视为无效输出并回退。
- Ollama 与系统 OCR 均失败：抛出包含两条原因的聚合错误。
- 配置关闭回退：保留原始模型错误，便于诊断。

## 测试

- 纯函数：地址规范化、请求体隔离、固定采样参数、围栏重复检测、精确循环检测、外层围栏清理、Markdown/LaTeX 原样保留。
- 管线：正常流不回退、生成失败回退、无效输出回退、关闭回退、双重失败、新请求取消旧请求、回退中的旧请求作废。
- 传输层：首响应前取消、NDJSON 跨分块解析与 HTTP 错误传播。
- 系统回退：当前 base64 参数透传、独占临时图与回收。
- 源码契约：识别服务注册、Rust 白名单、完整语言枚举、结构化输出不被删除换行。
- 构建：定向 `node:test`、Vite 构建、Cargo 检查与 Windows release 构建。

## 迁移策略

无迁移，直接新增。现有系统 OCR、Tesseract 与云 OCR 配置保持可用；只在本机配置中把新服务放到识别列表首位，使 Ctrl+E 默认使用 GLM-OCR。
